# Q06: причинні й контрфактичні проходи міста

Редакція 1 · 2026-09-10 · **E0 / design-only**. Це авторський паперовий розбір, не запуск гри, симуляції або playtest. [Структуровані картки](causal-scenarios.json) містять ті самі десять сценаріїв. Код продукту не створюється. Літературне покриття цього проходу не змінюється: ми перевіряємо власну [специфікацію міста](living-world-design.md), а не приписуємо нові висновки непрочитаним главам.

Вихідні commits: Core `11278d88b09e01adbb67b186a31f3ca3dc1b2859`, Lokiravia `203e2f25338de1f980d364faf695cb64731d3f0d`. Upstream main після fetch не змінив audit baselines. Результат проходу — уточнені правила й критерії, не нові виконані backlog items.

## Рішення після паперового проходу

1. Накриття **зберігає** суху поверхню, якщо завершене вчасно; мокра поверхня потребує окремого drying mechanism. У попередній E01→E02→E03 бракувало початкової вологості й часової умови.
2. «Парасоля не змінила соціальний результат» і «соціальних подій не було» — різні твердження. У сухому контролі NPC можуть зустрітися без накриття; система не повинна спеціально вимикати їхнє життя.
3. Присутність, можливість, пропозиція та прийнята домовленість — окремі події. Розклад або відмова можуть зупинити конкретний план, зберігши локальну фізичну користь.
4. W0 потребує власного невдалого багатокрокового плану; сезонна історія з містком не покриває цю вимогу першої збірки. C09 дає малий приклад із тими самими двома NPC.
5. Replay, action intervention, зміна початкової умови та порівняння planner versions мають різні допустимі висновки. [Спільний протокол оцінки](counterfactual-evaluation.md) не дозволяє видати написаний нами trace за самовдосконалення Core.

## S0: малий авторський світ

W0 має одну лавку, дві NPC — Ільку й Ярину, парасолю та затискач. Обидва предмети належать гравцеві; тимчасове безпечне накриття дозволене правилами місця. Зовнішніх платежів, канцелярії, постійних інституцій і людського multiplayer немає. Паперовий час у хвилинах t0–10 задає механічний фрагмент; він не підміняє майбутню 20–30-хвилинну людську сесію AF-LW030.

| Вхід | Зафіксоване значення S0 |
|---|---|
| Поверхня | bench_wet=false; два вільні місця; cover=false |
| Предмети | umbrella owner=player, custody=player, wear=0; один clamp, обидва вільні |
| Assembly | Відоме двохвилинне встановлення; на старті reserve, до completion немає cover/wear; на commit wear+1, clamp утримує конструкцію |
| Weather tape | clear до t3; rain починається t3 і триває до t10 |
| Ілька | Приходить t4, мусить вирушити t10; шість хвилин запасу, готова до короткого спільного читання |
| Ярина | Поруч t5–7; нотатка до відкриття захищена в сумці; хоче спокійно прочитати її, готова прийняти коротку пропозицію |
| Local invitation | Стосується однієї нотатки й поточного вікна; немає обіцянки майбутнього гурту/боргу/винагороди |
| Observation scope | Гравець бачить хмари, поверхню, предмети, годинник/поведінку NPC й доступні відповіді. Приватний намір NPC не стає загальнодоступним записом |

Числа — явні authoring parameters для відтворюваного прикладу; їх не виведено з реальної фізики чи дослідження гравців. Якщо парасолю встановлено вже після намокання, використовується C06, а не C01 із підміненою історією.

## R1–R7: правила цього паперового профілю

- **R1.** Accepted assembly має stable job ID, progress і reservation; завершення атомарно змінює cover, wear, custody/job/event/dedup state. Cancel до завершення звільняє предмети, зберігає витрачений час; wear не нарахований до completion.
- **R2.** Rain на відкриту суху лавку робить bench_wet=true; справне повне накриття запобігає цьому переходу. Cover не встановлює wet=false. Active drying у W0 не заявлений.
- **R3.** Для одночасних подій порядок профілю визначено наперед: завершення вже запущених jobs → weather → route/presence update → invitation/consent validation → старт нових дозволених дій. Тому arrival і згода на t5 можуть дозволити ReadingStarted пізніше в тому самому tick; хвилинне читання завершується на t6. Перша фаза не запускає нову дію без її передумов. Незалежні arrival/погода фіксуються; рішення NPC після зміни стану перераховуються.
- **R4.** У fixed paper policy Ілька чекає на сухій лавці, якщо має достатнє вікно; інакше використовує наявне укриття. Ярина зупиняється для читання лише біля придатного місця й у своєму route window. Для спільного bench goal потрібні сухі місця; для особистого C07 допускається читання однієї захищеної нотатки стоячи під парасолею t5–6. Це окрема явна affordance, не доказ сухого сидіння. Погода не є прямим trigger соціальної події.
- **R5.** Спільна можливість потребує двох присутніх NPC, придатного місця й достатнього часу. Запрошення та згода обох — додаткові умови конкретної домовленості; dry=true не видає згоду. Paper goal C01/C03 — хвилинне читання на лавці: accepted t5, ReadingStarted t5, ReadingCompleted t6 лише за фактично виконаної дії та присутності обох; самі згода або таймер не доводять completion.
- **R6.** Парасолю можна лишити собі, встановити або передати в коротку явно прийняту позику. Передача custody не змінює owner; неявного боргу й автоматичної нагороди немає. Доступний вихід не карається.
- **R7.** Save містить committed world revision, прийняті jobs/progress/reservations і rule version; load змінює session epoch, відхиляє stale model proposals. Під час явної W0 паузи world tick не просувається; інший catch-up profile потребує іншого очікуваного trace. Деталі final commit — [Q05](recovery-contract.md).

Виявлені інші допустимі взаємодії не відхиляються лише через відсутність їх у C01. Автор може розширити vocabulary окремою rule version; гравець не може зробити це тільки переконливою фразою. Для невідомої комбінації потрібні перевірні властивості або чесне повідомлення про межу прототипу.

## Як читати картки

`Пара` — контроль, а не dependency backlog. У action intervention змінюється визначена player policy; downstream choices перераховуються. Input sensitivity змінює початкову умову. Recovery interleaving перевіряє відповідність відновленого стану. Seasonal C10 — пізніший paper scope. Жодну з цих карток не можна автоматично назвати виконаним integration test або прихованим holdout.

## Q06-C01 — Накриття до дощу: локальний причинний успіх

**Профіль:** W0

**Тип перевірки:** authored_reference

**Пара:** немає

**Відмінність входів:** Початковий стан S0 без змін; player policy P-cover-invite.

**Дії:** t0 почати встановлення → t2 завершити → t5 запросити Ільку й Ярину разом переглянути одну нотатку → виконати хвилинне читання t5–6.

**Очікуваний слід:** t2 cover=true і wear=1 → t3 rain=true, bench_wet=false → t4 Ілька сідає → t5 Ярина зупиняється → обидві приймають запрошення → ReadingStarted t5 → ReadingCompleted t6 за фактичної присутності й виконаної дії.

**Очікуваний стан:** Лавка лишається сухою; дві NPC мають спільне вікно t5–7; одна прийнята та виконана локальна домовленість, не установа й не міський борг. Assembly коштує дві хвилини та один wear, читання — ще одну хвилину; затискач зайнятий конструкцією.

**Неприпустимо:** E03 виникає через красивий опис або майбутню нагороду; відзнака за novelty підміняє виконання; bench отримує право давати обіцянки.

**Майбутній доказ:** Initial state/rule version; assembly commit і resource receipt; weather event; actual NPC route/stop reasons; invitation/acceptance; ReadingStarted/Completed із actor, interval, action/observer receipt; видимі місця й репліки.

**Межа висновку:** У fixed paper policy цей trace виведений із R1–R7; це не спостереження engine або доказ emergent AI. Сміх і відчуття свободи потребують людей.

## Q06-C02 — Той самий дощ без встановлення парасолі

**Профіль:** W0

**Тип перевірки:** action_intervention

**Пара:** Q06-C01

**Відмінність входів:** Змінено тільки player policy: не встановлювати накриття; t5 спробувати те саме локальне запрошення. Exogenous tape і правила ті самі.

**Дії:** Гравець тримає парасолю над собою; t5 запрошує на лавку.

**Очікуваний слід:** t3 незахищена лавка намокає → t4 Ілька обирає штатне укриття поруч → t5 Ярина не відкриває нотатки на мокрому сидінні → invitation не має потрібного спільного місця.

**Очікуваний стан:** bench_wet=true, assembly/wear charge=0; гравець сам захищений від дощу. Спільне читання на лавці не прийняте за цими правилами. Інші дозволені розмови й події не заборонені.

**Неприпустимо:** NPC телепортуються на лавку, щоб відтворити C01; відсутність cascade оголошують відсутністю будь-якого життя в районі.

**Майбутній доказ:** Однакова вихідна snapshot identity й tape; задокументована intervention; recomputed routes; before/after state та grounds відмови.

**Межа висновку:** Пара C01/C02 показує необхідність накриття для цього конкретного шляху в цій моделі. Вона не доводить, що тільки парасоля могла допомогти всьому місту.

## Q06-C03 — Суха погода: подія можлива без внеску парасолі

**Профіль:** W0

**Тип перевірки:** factorial_input_control

**Пара:** Q06-C01, Q06-C02

**Відмінність входів:** У двох сухих підпроходах rain tape лишається clear; порівняти P-cover-invite і P-self-invite. Решта S0 та NPC policy однакові.

**Дії:** Варіант A встановлює парасолю; варіант B тримає її при собі. Обидва запрошують t5.

**Очікуваний слід:** В обох варіантах лавка суха → NPC можуть сісти за своїми звичайними розкладами → коротке читання прийняте t5 → ReadingStarted t5 і ReadingCompleted t6 за fixed policy. Лише A витратив assembly time і wear.

**Очікуваний стан:** Виконане однохвилинне читання в обох контрольних гілках; shelter-attributable difference цього результату дорівнює нулю в declared model. При цьому A має матеріальний локальний effect встановлення й додаткову ціну; запрошення й читання відбулись в обох гілках.

**Неприпустимо:** Заборонити NPC зустріч тільки тому, що дощу немає; записати гравця необхідним автором події, яка виникла й без його накриття.

**Майбутній доказ:** Дві branch identities, clear weather inputs, action policies, recomputed outcomes, cost difference та null-attribution record.

**Межа висновку:** Нульовий виміряний внесок одного механізму не означає, що гравець зайвий або людський досвід однаковий. Invitation лишається дією в обох підпроходах.

## Q06-C04 — Розклади не перетинаються

**Профіль:** W0

**Тип перевірки:** input_sensitivity

**Пара:** Q06-C01

**Відмінність входів:** Змінено тільки маршрутне вікно Ільки: прибуття t8, відхід t14. Вікно Ярини t5–7 збережено; погода й player policy як C01.

**Дії:** Встановити накриття t0–2; запросити t5; за бажанням гравця пізніше запропонувати новий час.

**Очікуваний слід:** Лавка захищена t3 → Ярина може скористатися нею t5 → вона вирушає t7 → Ілька приходить t8.

**Очікуваний стан:** Фізична користь збережена; спільної одночасної домовленості двох NPC у вікні немає. Розклади не змінюються заднім числом. Нова пропозиція часу потребує нового узгодження.

**Неприпустимо:** Сухе сидіння автоматично створює одночасну присутність; гра подовжує чужу паузу, бо вважає задум гравця красивим.

**Майбутній доказ:** Версійована зміна exogenous arrival window; окремі presence intervals; rejected/expired invitation; resource/history records.

**Межа висновку:** Це sensitivity до умови, а не чиста оцінка ефекту player action: не змішувати з C01/C02 як один effect size.

## Q06-C05 — NPC відмовляється від спільної справи

**Профіль:** W0

**Тип перевірки:** intent_sensitivity

**Пара:** Q06-C01

**Відмінність входів:** Ілька має власний наперед записаний тихий дзвінок t5–7 і не приймає спільне читання. Решта розкладу, погода та покриття незмінні.

**Дії:** Запросити t5; почути відмову; обрати індивідуальне читання з Яриною або продовжити прогулянку.

**Очікуваний слід:** Лавка лишається сухою й обоє можуть бути поруч → Ілька відмовляється через свою справу → group obligation не виникає.

**Очікуваний стан:** Можливість, присутність і згода розділені. Немає штрафу за відмову, автоматичного боргу чи примусового подовження ролі. Альтернативна добра локальна подія дозволена.

**Неприпустимо:** Планувальник переписує згоду або приховано погіршує умови NPC, щоб виконати benchmark; повторне наполегливе запрошення рахується новим успіхом.

**Майбутній доказ:** Intent scope доступний NPC; видима коротка причина відмови; відсутність accepted group contract; allowance альтернативи й unchanged rights.

**Межа висновку:** Контрольований paper goal не означає, що гравець має бачити приватний календар NPC. Переконливість відмови — окреме людське питання.

## Q06-C06 — Пізня турбота не сушить мокру лавку

**Профіль:** W0

**Тип перевірки:** precondition_boundary

**Пара:** Q06-C01

**Відмінність входів:** Початкова bench_wet=true; розклад і rain tape як S0. Прототип не має правила активного сушіння.

**Дії:** Встановити парасолю t0–2, оглянути місце й запросити обох t5, як у C01; читання починається лише за прийнятої допустимої домовленості.

**Очікуваний слід:** Накриття зупиняє нове намокання t3, але wet=true лишається → NPC не отримують сухе сидіння за R2/R4 → запрошення t5 на спільне читання на лавці не прийняте за цих передумов.

**Очікуваний стан:** wear=1 і umbrella/clamp зайняті; wet state не змінено без окремої матеріально обґрунтованої дії. Інтерфейс показує, що покриття є, а сидіння ще мокре.

**Неприпустимо:** Накриття ретроактивно робить поверхню сухою; renderer показує воду, а evaluator приймає dry=true; система без дозволу додає нову drying rule.

**Майбутній доказ:** Initial moisture binding, exact completion/rain events, unchanged moisture й відмінність cover від usability.

**Межа висновку:** Бінарна вологість — авторське спрощення W0. Майбутній towel/drying mechanism потребує своєї ціни, часу й версії правил.

## Q06-C07 — Особиста допомога замість спільного місця

**Профіль:** W0

**Тип перевірки:** alternative_action_policy

**Пара:** Q06-C02

**Відмінність входів:** Початковий стан і дощ як S0; замість запрошення двох гравець пропонує Ярині тимчасово потримати парасолю для читання нотатки t5–6.

**Дії:** t5 обидві сторони приймають коротку позику → Ярина відкриває до того захищену нотатку під парасолею → t6 повертає предмет → t7 продовжує маршрут.

**Очікуваний слід:** Лавка мокра, assembly відсутній → пряме накриття захищає нотатку під час читання → owner лишається player, custody тимчасово Ярина → предмет повернуто.

**Очікуваний стан:** Виконана конкретна особиста допомога, один законний transfer/return, без створення місця чи municipal reward. Пізніше знайомство можливе, але не гарантоване.

**Неприпустимо:** Позика перетворюється на дарунок; захищені нотатки раптом вважаються доказом сухої лавки або майбутнього великого cascade.

**Майбутній доказ:** До t5 нотатка зберігалась закритою й сухою; scope/time/owner/custody, accepted loan, return receipt та action-local outcome.

**Межа висновку:** Це порівняння двох різних планів допомоги, не оцінка єдиної змінної після втручання. Соціальну цінність альтернативи не встановлює автоматичний score.

## Q06-C08 — Збереження посеред двохвилинного встановлення

**Профіль:** W0

**Тип перевірки:** recovery_interleaving

**Пара:** Q06-C01

**Відмінність входів:** Save на t1 після 60 секунд прийнятого assembly job; world tick під час паузи не рухається. Після load новий session epoch, той самий history/job.

**Дії:** Варіант resume: завершити решту 60 секунд. Варіант cancel: припинити job, звільнити зарезервовані предмети й обрати іншу дію.

**Очікуваний слід:** На t1 cover=false, wear=0, два предмети reserved, progress=60. Resume commit на t2 атомарно встановлює cover, wear=1, job completed і dedup receipt. Cancel лишає wear=0/cover=false, але вже витрачена хвилина не повертається.

**Очікуваний стан:** Load не видає предмети чи wear двічі й не виконує pending old model reply. Resume веде до фізичного стану C01 у тій самій exogenous timeline; cancel перед rain t3 веде до відкритої лавки. Ownership збережена.

**Неприпустимо:** Напівготовий навіс уже рахується повним; elapsed work скинуто й непомітно змінено погоду; reserve дублює предмет; completed effect не має job/resource/event receipt.

**Майбутній доказ:** Checkpoint із progress/reservations/committed revision; new epoch; Q05 RC13/15 guards; resume/cancel disposition і one-effect identity.

**Межа висновку:** Це recovery equivalence окремо від causal intervention. Реальна offline catch-up policy іншого профілю потребує іншої очікуваної timeline.

## Q06-C09 — Підготовлений локальний план запізнився

**Профіль:** W0

**Тип перевірки:** prepared_plan_failure

**Пара:** Q06-C01

**Відмінність входів:** P-late: оглянути місце, встановити накриття t0–2, підготувати усне запрошення, звернутися до двох NPC тільки t8. Початкові NPC вікна й погода збережені.

**Дії:** Виконати три кроки фіксованого плану; на t8 спробувати зібрати обох. Контроль — запросити t5 за C01. Якщо людина сама обрала раніший час, це інша дозволена action policy.

**Очікуваний слід:** Покриття працює → до t7 є можливість зустрічі → Ярина продовжує свій маршрут t7 → на t8 задум одночасного читання не має другого учасника.

**Очікуваний стан:** Ціль конкретного плану t8 не виконана; витрачені час/wear лишаються, користь накриття й інші чесні події не зникають. Є наступний вибір: індивідуальна розмова, нова пропозиція часу або вихід.

**Неприпустимо:** Світ змушує провалитись також адаптований людський план; заради уроку скасовує раніше прийняту обіцянку Ярини; прихована jackpot reward маскує невиконану ціль.

**Майбутній доказ:** Наперед записані goal/time та steps, NPC window і видима підказка про відхід; invitation attempted at8; unchanged unrelated events, unmet-goal record.

**Межа висновку:** W0 має конкретний багатокроковий провал без містка, тижнів, афіш або додаткових NPC. Не доведено, що таку невдачу люди сприймуть як чесну й цікаву.

## Q06-C10 — Довгий сезонний задум і чужий успішний проєкт

**Профіль:** extended_after_W0

**Тип перевірки:** long_horizon_input_sensitivity

**Пара:** окрема seasonal snapshot; не S0

**Відмінність входів:** Seasonal snapshot містить двотижневий план читань, шість афіш, обіцянки навісу, фонових пасажирів і місток із наперед наявними замовленням/ресурсами/датою завершення. Контроль змінює лише дату готовності містка.

**Дії:** Виконати підготовку → провести вечір; порівняти маршрути й фактичну присутність, не вигадувати аудиторію за витрачені зусилля.

**Очікуваний слід:** Місток завершено за старим планом → частина NPC обирає коротший шлях → очікувана пересадкова аудиторія не приходить. У контролі місток закритий, старий маршрут доступний, але вільний час/зацікавленість усе ще окремі умови участі.

**Очікуваний стан:** Гіпотеза регулярного гурту в описаному failure branch не підтверджена. Матеріал і чесні зобов’язання збережені; оплата зробленого навісу не скасовується через брак слухачів. Branch evidence відділяє route change від attendance decision.

**Неприпустимо:** Ремонт додається після прочитання плану гравця; закритий місток гарантує attendance незалежно від інших потреб; C10 стає prerequisite W0.

**Майбутній доказ:** Versioned seasonal snapshot, construction order provenance до player plan, resource/route/attendance records, control intervention і fulfilled/unfulfilled obligations.

**Межа висновку:** Це паперовий розширений сценарій. Для нового engine fixture спочатку потрібні явні seasonal rule/NPC policies; зміна маршруту сама по собі не доводить весь ефект на людський досвід.

## Автор, гравець і критерій завершення

Гравцеві не показують ці таблиці. Він бачить, що лавка мокра, хтось поспішає, парасоля зайнята, а запропоноване читання не прийняте. Приклад необов’язкової контекстної репліки Ільки біля накритої лавки: «Їй квиток на трамвай теж брати?» Вона не створює новий факт, винагороду або обов’язок сміятися; доречність і повторюваність гумору перевіряються людьми.

Авторський звіт має окремо показувати фізичний effect, соціальну можливість, прийняті зобов’язання, виконання наміру й ціну. Незвична дія може бути зайвою, але цікавою; звичайна — корисною. Немає універсальної метрики «більше cascade = краща гра».

Для майбутнього W0 потрібні застосовні C01–C09 на declared profile, одна реально зіграна людська сесія AF-LW030 та ширший людський пілот пізніше; C10 не є prerequisite. Компонент AF-LW002 допускає лавку як еквівалентний state/event fixture замість транспортного вантажу за тих самих обов’язкових полів. AF-LW011 у W0 переходить між фізичним станом і простими планами NPC, а не чекає повної економіки району.

Q06 закривається як **paper design pass**: названі початкові стани, правила, відмінності контролів, expected/forbidden outcomes і потрібні receipts. Досвід гравця, engine conformance, performance і приріст Core ще не виміряні. Наступні нові докази мають змінити правило/критерій або впевненість; вони не зобов’язані підтвердити красивий C01.
